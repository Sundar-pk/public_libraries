# Handoff planner: add PIT mutation testing as an optional stage in the CIB GitLab CI pipeline

Written for an AI assistant (or engineer) with direct access to the repos. Read sections 1 to 4 fully before touching anything. Everything marked **[seen]** was read from screenshots of real files. Everything marked **[assumed]** is unverified and must be confirmed in the repo before relying on it.

---

## 1. Goal

Run PIT (Java mutation testing, `pitest-maven`) as an **optional, opt-in stage** in the GitLab CI pipelines that are generated by `cib-pipeline` from each app's `.cib-ci.yml`.

Success criteria:
1. An app sets `pitest_scan: true` (and optionally `pitest_threshold: N`) in `.cib-ci.yml`, pushes, and the generated GitLab child pipeline contains a PIT job that runs, produces an HTML/XML report as a job artifact, and fails the pipeline only when the score is below the threshold.
2. Apps that do not set the flag see **no change at all**.
3. No commit is needed in any DevFactory repo (the user has no write access there).
4. Any change in `cib-pipeline` has a test fixture and passes the repo's tests.

Out of scope: Jenkins, Angular/Stryker (separate later task), changing DevFactory-owned components.

- The app's `.gitlab-ci.yml` includes (per parent.yml header comment **[seen]**):
  ```yaml
  include:
    - project: cib/ss/2slabs/itti/cib-pipeline
      ref: master            # or a feature ref / release like 1.59.0
      file: resources/pipeline-templates/gitlab/parent.yml
  ```
  The file is written by `cib-pipeline -glbu`.
- An earlier pipeline failed with *"file resources/pipeline-templates/gitlab/parent.yml does not exist"* when the `ref` pointed at a branch where that file had been removed. Pipelines later ran normally, so the ref was fixed. If it recurs, locate the file's new path via `git log --all --diff-filter=DR --name-status -M -- resources/pipeline-templates/gitlab/parent.yml`.

### 3.2 Two-level GitLab pipeline **[seen]**
`parent.yml` (in `resources/pipeline-templates/gitlab/`):
- `workflow.rules`: one pipeline per push (a branch with an open MR only gets the MR pipeline); tags allowed.
- `include` of `Production-mutualisee/IPS/IDO/gitlab-cicd/pipelines` `variables/.variables.yml` (defines `CI_REGISTRY`, which is *not* a native GitLab variable on this instance).
- `stages: [generate, run]`.
- Job `cib-generate` (stage `generate`): image `$CI_REGISTRY/jdkmvn:21-n16`, tags `ocp_s`, `needs: []`, cache key `cib-pipeline-jar` path `.cib-pipeline/`. Script checks tools (git curl java awk), reads `.cib-ci.yml`, finds the cib-pipeline `ref` from the app's `.gitlab-ci.yml`, **downloads the cib-pipeline jar** (SNAPSHOT for `master`, release version otherwise, from Artifactory; vars `ARTIFACTORY_USER/PASSWORD`, `CIB_PIPELINE_MAVEN_REPOSITORY`; `version.txt` at that ref of the mirror says which version), then runs `cib-pipeline -glc` to generate `child.yml` as an artifact. Nothing is committed back.
- Job `cib-run` (stage `run`) triggers `child.yml` as a child pipeline and forwards `CIB_COMMIT_BRANCH`, `CIB_MR_IID`, `CIB_MR_TARGET_BRANCH`, `CIB_PARENT_CONTRACT`.

**Critical nuance:** the generator is a **jar fetched from Artifactory**, not just templates read from the git ref. So changing generator code or templates may require **building and publishing a new cib-pipeline jar/snapshot** before an app pipeline sees it. This corrects an earlier "probably no jar needed" answer. Find out: how are feature branches of cib-pipeline built and published (CI job in the cib-pipeline repo? Bitbucket pipeline?), what version string does a feature branch get, and how an app can point at it (`ref:` plus `version.txt`).

### 3.4 Evidence that DevFactory jobs are extensible **[seen in a local copy named devfactory-driven-pipelines]**
- `pipelines/iaas/.ciintegrate.yml` redefines `publish-package:` and `scan-sonarqube:` with extra `variables:` (KUBERNETES_CPU/MEMORY, `MAVEN_CLI_OPTS: "-U --batch-mode --errors --fail-at-end --show-version -DskipTests -DskipITs -DdeployAtEnd=t..."`) and `cache:` (`**/target`, `.m2/repository`, `**/node_modules/**`). That is GitLab's same-name job merge.
- `template.yml` contains a hidden template job `.scan-sonarqube` ("the default sonar scanner") that other jobs extend (`scan-sonarqube-mvn`, `-dotnet`, ...).
- `run-test-custom.yml` and `.utils-ci-test.yml` exist, which may be a documented hook for custom test jobs. **Read them first.**
- The components use GitLab `spec: inputs:` (e.g. `factory_service_version`), so inputs and rules are configurable per include.

GitLab features that let you add a job without committing to DevFactory: define a new top-level job in the generated `child.yml`; `extends:` a hidden job from an included template (inherits image, tags, cache, settings); override/merge an existing job by name; `include:project` a template file hosted in cib-pipeline (which you own) with its own `spec: inputs`.

## 4. Verified results from local work (reuse these)

### 4.1 PIT works locally
- Java 17 (Temurin 17.0.20.1), Maven, Spring Boot app `blank-boot`, JUnit 5.
- `pitest-maven` **1.25.7** works (the old 1.4.5 / 1.13 failures were version problems; "minion exited abnormally" disappeared). `pitest-junit5-plugin` **1.2.1** must be declared as a plugin dependency in the app pom:
  ```xml
  <plugin>
    <groupId>org.pitest</groupId><artifactId>pitest-maven</artifactId><version>1.25.7</version>
    <dependencies><dependency>
      <groupId>org.pitest</groupId><artifactId>pitest-junit5-plugin</artifactId><version>1.2.1</version>
    </dependency></dependencies>
  </plugin>
  ```
  Invoking `org.pitest:pitest-maven:1.25.7:mutationCoverage` with an explicit version from the CLI still picks up the pom's plugin dependencies (this is what worked locally).
- First full run: 710 mutations, 92 killed (13%), 469 with no coverage; line coverage 570/1511 (38%); test strength 38%; ~4.5 minutes; build failed on the default threshold of 70 (`BUILD FAILURE: mutation score of 13 is below threshold of 70`). Use `-DmutationThreshold=0` for an informational baseline.
- Useful flags: `-Dthreads=4`, `-DtargetClasses=... -DtargetTests=...`, `-DwithHistory`, `-DoutputFormats=HTML,XML`, `-DtimestampedReports=false` (fixed report path `target/pit-reports`).
- Local TLS problem was only the corporate Artifactory truststore on a portable JDK; irrelevant in CI.
- CI runner image is JDK **21** (`jdkmvn:21-n16`) while the app targets Java 17 (child fixture says `language_version: '8'` for the sample). Verify PIT 1.25.7 on the runner JDK in the first CI run. The module compiles to its own target level, so this is normally fine.

## 6. Design options (choose after answering section 5)

**Option A: standalone job emitted by the generator.** Self-contained job in `child.yml` (own image, tags, Maven settings generated from `ARTIFACTORY_*`). Fewest dependencies on DevFactory; works if image and runner are valid. Draft below.

**Option B: job that `extends:` a DevFactory hidden build job.** Inherits image, tags, cache, Maven settings and authentication; override only `stage`, `script`, `rules`, `needs`, `artifacts`. Most robust *if* a hidden template exists and is stable across `services@` versions. Pin-sensitive: when DevFactory bumps `ref`, it can break.

**Option B2 (recommended if allowed): template hosted in cib-pipeline, included by the generated child.** Put `resources/pipeline-templates/gitlab/component-pitest/template.yml` in cib-pipeline using `spec: inputs:` (stage, rules, version, threshold, pom path, extra opts, allow_failure), then the generator only adds one `include:project: cib/ss/2slabs/itti/cib-pipeline` block plus the `mutation` stage, exactly like the existing DevFactory component includes. Keeps the job definition in YAML, readable and testable, and removes a lot of generator string-building. Check question 7 first.

**Option C: ask the DevFactory team for a `component-pitest`.** Long-term clean option. Mention in the final report; do not block on it.

**Interim proof (no generator change):** add the same job to a test app's own `.gitlab-ci.yml` (`stage: run`, remove `needs:`) behind `when: manual`, `allow_failure: true` to prove the Maven command, image, Artifactory access and report artifacts work in CI. Do this early; it de-risks everything else.

### Draft job (Option A, adapt for B/B2)
```yaml
pitest:
  stage: mutation
  image: $CI_REGISTRY/jdkmvn:21-n16          # confirm from build-code log
  tags: [ocp_s]                               # confirm
  needs:
    - job: build-code
      artifacts: false
  interruptible: true
  rules:
    - if: '$CIB_MR_IID'
    - if: '$CIB_COMMIT_BRANCH =~ /^(?:develop)$/'
  allow_failure: true                         # generator sets false when threshold > 0
  variables:
    PITEST_VERSION: "1.25.7"
    PITEST_THRESHOLD: "0"
    PITEST_POM: "pom.xml"
    PITEST_EXTRA_OPTS: ""
    MAVEN_MIRROR_URL: "<artifactory_host>/artifactory/<artifactory_repo>"   # generator fills from .cib-ci.yml
  cache:
    - key: default
      paths: [.m2/repository]
  script:
    - |
      set -eu
      cat > pit-settings.xml <<EOF
      <settings>
        <servers><server><id>artifactory</id><username>${ARTIFACTORY_USER}</username><password>${ARTIFACTORY_PASSWORD}</password></server></servers>
        <mirrors><mirror><id>artifactory</id><mirrorOf>*</mirrorOf><url>${MAVEN_MIRROR_URL}</url></mirror></mirrors>
      </settings>
      EOF
    - mvn -s pit-settings.xml -Dmaven.repo.local=.m2/repository -B --no-transfer-progress -f "$PITEST_POM" test-compile org.pitest:pitest-maven:${PITEST_VERSION}:mutationCoverage -DmutationThreshold="$PITEST_THRESHOLD" -DoutputFormats=HTML,XML -DtimestampedReports=false $PITEST_EXTRA_OPTS
  artifacts:
    when: always
    expire_in: 7 days
    paths: ["**/target/pit-reports/"]
```
Design notes:
- Add `mutation` to `stages:`. Prefer the **end** of the list. If it sits second, every later stage (`sonar`, `publish`, `sbom`, `security`) waits for PIT unless its jobs use `needs:`. With `needs: [build-code]` the job starts as soon as the build passes regardless of stage order.
- `needs: build-code` requires that job to exist on every pipeline where PIT runs. PIT rules must be a subset of the build rules (they are: MR and develop).
- Threshold: `0` = report only; `> 0` fails the job and the generator must then emit `allow_failure: false`. Suggested ratchet: start 0, then just below the current score (local was 13), then raise.
- Heredoc inside a YAML `|` block: the `EOF` line must have the same indentation as the `cat` line so it ends up at column 0 after dedent.
- Multi-module: `PITEST_POM` must point at the module (`blank-boot/pom.xml`) or use `-pl blank-boot -am`.
- Runtime ~4.5 min locally for ~710 mutants; consider `-Dthreads`, `targetClasses`, and `withHistory` (needs a cache of `target/pit-reports/history`).

## 9. Pitfalls and nuances checklist

- A fixture edit is not a pipeline change (see section 7).
- The cib-pipeline generator is a downloaded jar; a template-only change might need a published build. Verify before debugging "nothing changed".
- Wrong `ref` in the app's `.gitlab-ci.yml` (pointing at a branch without `parent.yml`, or at `master` that lacks your change) is the most common reason a new stage doesn't appear.
- `needs:` on a job that is not created by rules in that pipeline makes the whole pipeline invalid. Keep PIT rules a subset of the `build-code` rules, or use `needs: [{job: build-code, optional: true}]`.
- Stage order: a mid-list `mutation` stage blocks later stages for jobs without `needs`.
- The child pipeline starts only if `CIB_PARENT_CONTRACT == "1"`; keep rules on `CIB_*` variables, not on `CI_*` ones (the child doesn't see the merge request source).
- CI/CD variables are masked; never echo them. Keep the heredoc unquoted so `${ARTIFACTORY_*}` expand, and keep the file out of artifacts (don't include `pit-settings.xml` in `artifacts.paths`; it contains the password). Delete it at the end of the script if you want to be safe.
- Passwords containing XML special characters (`&`, `<`) would break the settings file; prefer writing it via a safer method if that is a concern.
- `$CI_REGISTRY` is defined by the IDO variables include, not by GitLab; confirm it resolves in the child.
- JDK mismatch: runner image JDK 21 vs app target 17/8. If PIT has trouble, try a JDK 17 image if one is allowed, or set `JAVA_HOME` accordingly.
- PIT default threshold is 70 and fails builds; always pass `-DmutationThreshold`.
- PowerShell quoting: `-Dfoo.bar=...` arguments get split at dots; use `--%`, quoting, or run in cmd. Not relevant inside CI jobs (sh/bash), relevant for local reproduction.
- Windows CRLF in the clone is fine for YAML, but keep fixtures' line endings consistent with the repo's `.gitattributes`.
- Don't commit anything that belongs to DevFactory repos; if a local copy sits in the workspace, keep it read-only.
