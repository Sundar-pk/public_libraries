Onboarding an Application to DevLake (Engineering Metrics)

1. Purpose and audience

This page explains, step by step, how an application is onboarded to Apache DevLake so that its delivery, quality and team-health metrics appear in the engineering-metrics dashboards. It is written for application managers and tech leads (who provide the information) and the DevLake admin team (who configure the platform).

Onboarding follows one of two toolchain paths, depending on where the application's tools are hosted. Please follow the path that matches your application.

2. Step 1: Identify your toolchain

Tool CIB toolchain ITG toolchain
Source control Bitbucket Server GitLab
Issue tracking Jira CIB Jira Group
Code quality SonarQube CIB SonarQube Group
CI / build Jenkins CIB Jenkins Group
DevLake connection type Bitbucket Server, Jira, SonarQube, Jenkins GitLab, Jira, SonarQube, Jenkins

Note: If your application uses tools from both toolchains (for example, Bitbucket with Jira Group), please tell us in the request form. We will set up each tool under its own connection.

3. Step 2: Gather the information

Please collect the following before raising the request. Items marked with an asterisk (*) are mandatory.

# Information Example / guidance
1 Application name* Name used for the DevLake project and dashboards
2 Toolchain* CIB or ITG
3 Repository URL(s)* Bitbucket Server project/repo (CIB) or GitLab project path (ITG). List every repository that belongs to the application
4 Production branch* For example main or master
5 Jira project key and board* For example ABC and the board name or ID
6 Jenkins URL* The URL up to and including your project name, from the Jenkins CIB or Jenkins Group instance (see Step 4)
7 Jenkins deployment job name(s)* The job(s) that deploy to production
8 SonarQube project key For example com.company:app-name
9 Merge strategy Merge commit (recommended) or squash / rebase
10 Jira ticket key in PR titles or branch names Yes / No (see "Practices that keep data accurate")
11 Application manager and technical contact* Names and email addresses
12 History to load Suggested: last 6 months

4. Step 3: Confirm access

DevLake reads data using service or API tokens, not personal credentials. Please confirm the following:

Tool What is needed
Bitbucket Server (CIB) or GitLab (ITG) Read access to the repositories listed above
Jira CIB or Jira Group Read access to the Jira project and board
SonarQube CIB or Group Browse access to the Sonar project
Jenkins CIB or Jenkins Group Read access to the jobs under your project URL, using an API token from a service account

Note on Jenkins: Jenkins URLs are specific to the project name, so each application normally has its own Jenkins connection (its own URL and token). Bitbucket, GitLab, Jira and SonarQube typically use one shared connection per instance, and the application is added to it as a scope. A service account token is recommended for Jenkins because tokens tied to a personal login can stop working when sessions or passwords change.

5. Step 4: Request onboarding

Please raise the request with the DevLake admin team, using the information from Step 2.

  • Request channel: {insert request link / mailbox / ticket queue}
  • Contact: {insert DevLake admin contact}

The admin team will complete Steps 5 to 8.

6. Step 5: DevLake connections (admin team)

Tool Connection Created
CIB: Bitbucket Server, Jira CIB, SonarQube CIB One connection per instance Once, then reused by every CIB application
ITG: GitLab, Jira Group, SonarQube Group One connection per instance Once, then reused by every ITG application
Jenkins CIB / Jenkins Group One connection per application (endpoint = the project-level Jenkins URL) At onboarding

Where a tool is served over an internal certificate, the DevLake environment must trust the corporate CA certificate for that host. This is checked at this step.

7. Step 6: Create the DevLake project (admin team)

  1. Create a DevLake project named after the application.
  2. Enable the DORA metrics option for the project.
  3. Add the application's resources to the project, from the matching connections:
    • repositories (Bitbucket Server or GitLab);
    • Jira board;
    • SonarQube project;
    • Jenkins job(s).
  4. Apply the scope configuration (next step).

8. Step 7: Apply the scope configuration (admin team)

Setting What is configured
Deployment detection Jenkins job name pattern that identifies a production deployment
Production environment Pattern identifying the production branch / environment (for example ^(main|master)$)
Issue types Jira types mapped to Requirement, Bug and Incident
PR to issue linking Pattern that finds the Jira key in PR titles or branch names
Data range Start date for the first collection

9. Step 8: Run the first collection and verify

  1. The admin team runs the first collection and sets a daily or periodic schedule.
  2. The admin team and the application manager check the results together:
Check Expected
Collection completes without errors All tools show success
Dashboard shows the application The application is selectable in the project filter
Pull requests and commits appear Counts look reasonable for the period
Jira issues appear Bugs and requirements are classified correctly
Deployments appear Production deployments are listed, so DORA metrics are calculated
Sonar data appears Coverage, bugs and code smells are visible
  1. Dashboard access is given to the application's team as view-only.

10. Practices that keep data accurate

Please consider the following so that the metrics are comparable across applications.

  • Merge strategy: use merge commit and avoid squash or rebase merges where possible. Squashing changes commit identifiers, which can leave deployment-time metrics empty.
  • Ticket keys: include the Jira key in PR titles or branch names, so delivery can be traced back to requirements.
  • Branch naming: use a consistent production branch name.
  • Jenkins job naming: use a clear, consistent name for production deployment jobs.
  • Jira hygiene: keep issue types and statuses up to date.

11. Common issues and resolutions

Symptom Likely cause Resolution
Jenkins returns 401 Token expired, or tied to a personal login Issue an API token from a service account and update the connection
Jira returns 429 (rate limit) Collection rate too high The admin team lowers the connection's rate limit
Certificate or TLS error Corporate CA not trusted by DevLake Admin team adds the CA certificate for that host
Dashboard empty Wrong time range, or project not selected Check the dashboard time range and the project filter
Deployment-time metric empty Squash or rebase merge, or deployment pattern not matching Review the merge strategy and the deployment job pattern
Repository missing Not added to the project scope Send the repository URL to the admin team
